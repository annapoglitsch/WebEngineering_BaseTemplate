Theory question: How does an ES module differ from a classic script with respect to scope, strict mode, loading, and bindings? Explain why the module boundaries you chose make the application easier to maintain.
Scope: Normally declarations lack into window/global scope. With ES-Modules variables stay in local file. Every module has its private space
Strict Mode: In classic script u need to use "use strict" otherwise it is not strict. In ES Modules its automatically in strict mode.
Loading: Classical a script is loaded synchronously. Loads from the top to the bottom. ES Modules load asynchronously. First the browser loads all imported files and resolves dependencies and does it then in the correct order.
Bindings: There is no import export scheme. If you share code between files you need to use window. However, with ES modules you have live bindings -  if a variable changes in export the import copy also adapts.

ES Modules make it easier because i can split the script theme vise without destroying the code or connections. You get a better overview. -> Separation of Concerns

Synchrone Fehler springen sofort den Call stack hoch, bis sie von try/catch gefangen werden. Rejected Promises hingegen reisen durch die gesamte .then-Kette, überspringen alle .then blöcke und werden erst vom nächsten catch aufgefangen

und entschieden ob die anwendung weitermachen kann

AI:
Synchrone Exceptions werden mit throw ausgelöst und können über den Call Stack nach oben weitergegeben werden.
Bei asynchronem Code führt ein Fehler normalerweise zu einem rejected Promise, das mit await/try-catch oder .catch() behandelt werden kann.
Fehler sollten möglichst dort gefangen werden, wo man sinnvoll auf sie reagieren kann, zum Beispiel in einer zentralen Fehlerbehandlung.
Wenn man jeden Fehler direkt an seiner Quelle abfängt, kann man Fehler verschlucken oder wichtige Informationen verlieren.
Dadurch wird die Fehlersuche schwieriger.

Theory question: Explain the relationship between async/await, promises, the microtask queue, and the browser event loop. Also explain why an arrow function is not always an interchangeable replacement for a regular function, particularly regarding this.
JavaScript kann nur eine Sache gleichzeitig tun. Damit fetch() zb die Seite nicht einfrieren gibt es mehrere Warteschlangen.
microtask queue: hier landen promise callbacks, alles was nach .then, catch oder await passiert
Microtasks haben im CallStack vorrang
await pausiert nur die eine async-Funktion, nicht das ganze Programm. Und alles, was nach einem await kommt, läuft als Microtask
Promise.allSettled() selbst ist ein Promise. Der Code nach dieser Zeile (die Filterung, das DOM-Update) wird erst als Microtask ausgeführt, sobald alle bearPromises fertig sind
(egal ob erfolgreich oder fehlgeschlagen). Bis dahin läuft der Rest deines Programms (z. B. andere Event-Listener) ungehindert weiter.
Eine normale Funktion (function() {}) bekommt ihr eigenes this, das davon abhängt, wie sie aufgerufen wird. Eine Arrow Function (() → {}) hat kein eigenes this — sie "erbt" das this aus dem umgebenden Scope

AI:
async/await arbeitet mit Promises; wenn ein Promise fertig ist, wird die Fortsetzung typischerweise als Microtask eingeplant, die vom Event Loop ausgeführt wird.
Arrow Functions unterscheiden sich von normalen Funktionen vor allem dadurch, dass sie kein eigenes this besitzen.
